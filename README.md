## 2026年10月：資料に基づくM1〜M6比較実験

「自主研究での実験モデル.pdf」と「評価指標.pdf」（2026年10月1日）に基づく実験は、
以下の共通プログラムを使用する。**まずM2 → M3/M4 → M5 → M1/M6 → 詳細ルール**の順に確認する。
既存のByteTrack版は追加ベースラインとして残すが、資料のYOLO-only（M2）とは区別する。
実装条件・資料との対応・評価式の扱いは [実験仕様](EXPERIMENT_PROTOCOL.md)にまとめた。

### 実験に使うプログラム

| プログラム | 用途 |
| --- | --- |
| [run_tracking_experiment.py](run_tracking_experiment.py) | M1〜M6の共通実行、同期／非同期、P/G/R条件、CSV・動画保存 |
| [prepare_experiment_data.py](prepare_experiment_data.py) | 2段階median背景作成、画像・blobパッチ抽出、ラベル確認 |
| [train_blob_cnn.py](train_blob_cnn.py) | M1用ResNet-18の転移学習と、テスト集合の3分類評価 |
| [evaluate_tracking_experiment.py](evaluate_tracking_experiment.py) | TSR/AUC、CLE/NCLE、Coverage、Lost/Recovery、候補Recall |
| [evaluate_score_events.py](evaluate_score_events.py) | シュート単位の成功F1・Macro-F1・判定不能を集計 |

| ID | 実装した追跡方式 | 検出がないフレーム |
| --- | --- | --- |
| M1 | 2段階median背景差分 → blob → 3分類CNN → 膨張枠IoU・距離による対応付け | missing。LostではCNNのGrid再探索が可能 |
| M2 | YOLOの検出と最小限の候補対応付け | missing。ByteTrack/KF/KCFなし |
| M3 | YOLO＋等速KF | 期限付きKF予測 |
| M4 | YOLO＋KCF | KCF画像追跡。失敗時はmissing |
| M5 | YOLO＋KCF＋KF | KCF観測をKFで検証・補正、観測なしは期限付き予測 |
| M6 | M5＋blob ROI内のYOLO | M5と同じ。候補なし・過多・Lost等で全画面fallback |

M1のCNNはbbox検出器ではなく、切り出しを`background / ball / player`に分類する。
リングは共通YOLO検出器または手動固定矩形で扱う。M1はResNet-18へ置換した研究版であり、
資料が紹介するVGG-M論文の忠実再現ではない。

### 手順1：環境と撮影データを準備する

PowerShellをこのプロジェクトで開き、Python 3.12の仮想環境を使う。
既存の`.venv`が動く場合、作成コマンドは不要。

```powershell
cd "D:\自主研究\independent_reserch"
py -3.12 -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
# NVIDIA GPU / CUDA 12.8版を使う場合はこちら
python -m pip install -r requirements-cuda.txt
python -c "import cv2, torch; print('KCF:', hasattr(cv2, 'TrackerKCF_create')); print('CUDA:', torch.cuda.is_available())"
```

`requirements.txt`の壊れていた参照関係は修正済み。Ultralyticsが通常版OpenCVも入れる環境で
KCF APIが見つからない場合は、`python -m pip install --force-reinstall --no-deps opencv-contrib-python==4.14.0.94`
でcontrib版を入れ直して確認する。モデル・データ・学習結果はGit管理対象外。

固定カメラで通常移動、保持、パス、シュート、リング接触、部分／完全遮蔽、画面端を撮影する。
各撮影条件で、**実験の前に同じ画角・解像度の背景用動画**も撮影する。
背景作成にテスト動画の未来フレームを使わない。カメラ移動・ズームありは別条件にする。
同じ動きを使う比較は、ライブで撮り直すのでなく同一録画を全方式へ入力する。

### 手順2：画像を切り出す前にデータを分割する

撮影日・セッション単位でtrain/val/testを決める。目安は60/20/20%だが、各集合に
成功・失敗・遮蔽・小球等の条件が入るよう件数を確認する。**隣接フレームのランダム分割は禁止**。
同じシュートの切り抜き・別ファイル名のコピーも同じ集合に置く。testは最後まで調整に使わない。

[sessions.csvの例](experiment_examples/sessions.csv)をコピーして、実ファイルに合わせて編集する。
パスはCSVのあるフォルダーを基準に解決する。同じsession_idは必ず同じsplitにする。
`background`列にはその動画の撮影条件に対応する背景PNGを指定する。

```csv
session_id,split,video,background
day01,train,raw/day01_shot01.mp4,backgrounds/day01.png
day02,val,raw/day02_shot01.mp4,backgrounds/day02.png
day03,test,raw/day03_shot01.mp4,backgrounds/day03.png
```

以降はこれを`datasets/sessions.csv`として保存した例。仮のファイル名は実際の動画名に置き換える。

### 手順3：背景を作り、正解付け用画像とblobパッチを抽出する

```powershell
# 18×18＝324フレームの2段階median。撮影セッションごとに実行
python prepare_experiment_data.py background --video datasets/raw/day01_background.mp4 --output datasets/backgrounds/day01.png
# day02、day03についても対応する背景を作成してから実行
python prepare_experiment_data.py extract --sessions datasets/sessions.csv --stride 6 --output datasets/annotation_v1
```

60fps動画の`--stride 6`は検出器・CNN学習候補を約10枚/秒で抽出する初期案。
blur、遮蔽直前／直後、リング接触は必要に応じ`--stride 1`で収集する。
この間引きは**学習画像用**。Lost/復帰の最終評価には全フレームのGTが必要。

出力は`images/train|val|test/`の原画像、`patches/`の余白付きblob画像、
`patches.csv`の未ラベル一覧、動画ごとの`*_gt_template.csv`（全フレーム、未注釈）、
`preparation.json`。画像から自動的に正解ラベルを決める処理はしない。
背景との差分閾値25、最小blob面積4px、余白倍率1.5が初期値。
候補Recallを見てval集合で決め、M1/M6とパッチ抽出で同じ設定を使う。

### 手順4：3種類の正解データを作り分ける

| 正解データ | 注釈対象 | 用途 |
| --- | --- | --- |
| YOLO用 | 原画像内のball/player/ringの各bbox | 検出器の学習・Ball/Ring AP評価 |
| CNN用 | 実際に抽出されたblobパッチ1枚のクラス | M1の3分類器の学習・混同行列 |
| 追跡GT | 全フレームの球・リングbbox、可視性、shot_id等 | TSR、NCLE、Lost/復帰、リング相対座標の評価 |

#### 4-A. YOLOの矩形ラベル

1. 原画像を矩形注釈ツールに読み込み、クラスを`0: ball`、`1: player`、`2: ring`に固定する。
2. 見える全対象を囲む。球は球本体、選手は身体全体、リングは**rim部分のみ**など、基準を最初に決める。
   ネット込みとrimのみの枠を混ぜない。小球は拡大表示して数pixelのずれも確認する。
3. 部分遮蔽で物体の位置・範囲を判断できる場合は、一貫した基準で注釈する。
   完全遮蔽中の球を推測して矩形化しない。位置不明の部分遮蔽を無理に負例画像へ混ぜず、
   学習から除外するなどの扱いを記録する。YOLO形式には一般的なignore領域がない点に注意する。
4. 検出器の自動ラベルを補助に使う場合も、見逃し・誤検出を人が全件確認する。
   未確認の「検出ゼロ」を背景の正解として扱わない。
5. YOLO形式で保存する。各画像と同名のtxtに`class_id x_center y_center width height`を1物体1行で記載。
   座標は画像幅・高さで割った0〜1の値。画像内の対象が本当にゼロなら空txtにする。
6. `datasets/detection/images/{train,val,test}`と`labels/{train,val,test}`を同じstemで対応させる。
   [detection.yaml](experiment_examples/detection.yaml)のpathとクラスを確認する。

```text
datasets/detection/images/train/day01_0000000.jpg
datasets/detection/labels/train/day01_0000000.txt
```

YOLO11n/sを同じval集合で比べ、採用した**1つの重みをM2〜M6で共用**する。

```powershell
yolo detect train model=yolo11n.pt data=experiment_examples/detection.yaml imgsz=960 epochs=50 batch=4 seed=42 project=runs/detect name=ball_ring_v1
yolo detect val model=runs/detect/ball_ring_v1/weights/best.pt data=experiment_examples/detection.yaml split=val
# モデル・閾値を固定してから一度だけ最終test評価
yolo detect val model=runs/detect/ball_ring_v1/weights/best.pt data=experiment_examples/detection.yaml split=test
```

50epoch・batch4は開始例で、最適値やGPUメモリへの適合を保証しない。
Ball AP50/AP50:95とRing AP50を別々に記録する。検出Precision/RecallはconfidenceとIoU閾値を固定して報告。
APのconfidence順位による評価と、運用時の固定閾値評価は区別する。

#### 4-B. M1用CNNのパッチラベル

1. `patches.csv`のpathにある画像を原画像と見比べる。ラベルは`ball`、`player`、`background`。
2. `ball`はボールが主対象として分離した候補。位置をblob枠から求めるので、
   「大きな選手領域のどこかに小球が写る」パッチを無条件にballへ分類しない。
3. 主対象が選手なら`player`、手・靴・ネット・ライン・影・反射などの誤候補は基準を決めて
   `background`へ。境界が曖昧なmerged blobは`ignore`にし、`ignore_reason`を書く。
   ボールを含むmerged blobの頻度自体は候補生成の弱点として別に記録する。
4. 停止球、blur、部分遮蔽、小球、明暗の違いを含める。きれいな球の切り抜きだけでは学習しない。
   背景誤検出を収集するhard negative miningはtrain/valだけで行い、testを再学習に戻さない。
5. 確認済み行だけ`reviewed=1`にする。採用しない画像も消して隠さず、ignore理由を残す。
   クラス件数・撮影セッション数を確認し、同じ場面の画像数だけでデータ量を増やさない。
6. 別の確認者による再点検、または時間を空けた再点検を行い、誤ラベルを修正する。

```powershell
python prepare_experiment_data.py validate-patches --manifest datasets/annotation_v1/patches.csv
python train_blob_cnn.py --manifest datasets/annotation_v1/patches.csv --output runs/blob_cnn/v1 --epochs 20 --batch-size 32
```

ResNet-18のImageNet重みから3分類へ転移学習する。クラス不均衡には損失重みを使い、
valのMacro-F1で`best.pt`を選ぶ。初回は事前学習重みのダウンロードが必要。
画像は107×107にresizeしRGB正規化。学習時だけ左右反転・色調変化を加える。
未確認ラベル、セッションのsplit混在、同一画像の別split混入はエラーになる。
同じ動画を再編集した別ファイルまで自動検出できるわけではないので、人も由来を確認する。

最終的な構成とCNN閾値（初期値0.7）をvalで固定した後、testだけを評価する。

```powershell
python train_blob_cnn.py --manifest datasets/annotation_v1/patches.csv --evaluate runs/blob_cnn/v1/best.pt --output results/blob_cnn_test_v1
```

`test_metrics.json`にGT行・予測列の混同行列、クラス別Precision/Recall/F1、Accuracyを保存。
**CNNの分類Accuracyと追跡成功率は別物**。M1全体の評価も必ず実施する。
4分類のリングCNNは今回使わない。静止リングがblobに出ない問題は共通リング検出で扱う。

#### 4-C. 全フレームの追跡GTとシュートラベル

抽出時の`*_gt_template.csv`を元動画で注釈し、[形式例](experiment_examples/tracking_gt.csv)に合わせる。
例の数値は書式確認用で、実験の正解ではない。

- `frame_index`：0始まり。`timestamp_s`：元動画の時刻。可変FPSでは実画像時刻へ修正する。
- `bbox_x,y,w,h`：対象ボールの枠。中心は枠から計算する。
- `ring_bbox_x,y,w,h`：評価用の正解リング枠。実行時の予測リングと別管理する。
- `visibility`：`visible`／`partial`（位置判定可能）／`occluded`（位置不明）／`out_of_frame`。
  後二者の球bboxは全て空欄。完全遮蔽中を線形補間したGTで評価しない。
- `shot_id`：1シュート1ID。`score`：`score`または`miss`。結果が確認できない動画は収集時に理由を記録する。
- `fast`、`small`：0/1。速度・球サイズの閾値はval段階で定義して固定する。

追跡注釈ツールの補間は補助として使い、急な動き・遮蔽・リング接触を全フレーム見直す。
同じ注釈済みtest動画・GTを全方式へ入力する。初期球選択やリング指定にtest GTを使う条件は、
通常評価と混ぜず「GT初期化／手動リング」の診断条件として記録する。

### 手順5：M1〜M6を同じ入力で実行する

まずofflineで精度・計算量を比較する。以下のモデルは手順4で学習したball/player/ringモデル。
`--output`は未作成のフォルダー名を指定する。

```powershell
# 毎フレーム検出のM2
python run_tracking_experiment.py --video datasets/raw/day03_shot01.mp4 --method M2 --model runs/detect/ball_ring_v1/weights/best.pt --s2-hz 0 --no-preview --output results/models/M2_every

# 同じ15Hzの検出頻度でM2〜M5を比較
foreach ($method in @('M2', 'M3', 'M4', 'M5')) {
    python run_tracking_experiment.py --video datasets/raw/day03_shot01.mp4 --method $method --model runs/detect/ball_ring_v1/weights/best.pt --s2-hz 15 --no-preview --output "results/models/${method}_15hz"
}

# blob ROIでYOLO推論するM6
python run_tracking_experiment.py --video datasets/raw/day03_shot01.mp4 --method M6 --model runs/detect/ball_ring_v1/weights/best.pt --background datasets/backgrounds/day03.png --s2-hz 15 --no-preview --output results/models/M6_15hz

# CNNでblob分類するM1。YOLOモデルは共通リング検出用
python run_tracking_experiment.py --video datasets/raw/day03_shot01.mp4 --method M1 --model runs/detect/ball_ring_v1/weights/best.pt --background datasets/backgrounds/day03.png --cnn runs/blob_cnn/v1/best.pt --s2-hz 0 --no-preview --output results/models/M1
```

`--record`で表示付きMP4も保存。プレビュー中は`Q`またはEscで終了。
標準COCO重みにはringがないため、動作確認で`--model yolo11n.pt`を使う場合は
`--ring X Y W H`で手動リングを指定する。値は元動画の実矩形に置き換える。
標準重みのsports ballはバスケットボール専用検出器ではない。

出力は`tracking.csv`（観測種別・球bbox・リング相対座標・時刻）、`detections.jsonl`
（候補ROI・推論時間・呼出し数）、`config.json`（条件・ハッシュ・環境）、`runtime.json`。
M1のCNNの自動初期化確認は2回。完全に同じ初期化待ち時間で比べる場合は`--confirm-frames 1`を明記する。

### 手順6：非同期・探索・リング切替を1項目ずつ比較する

```powershell
# 元動画の時刻で再生し、最新待機画像を優先する非同期版
python run_tracking_experiment.py --video datasets/raw/day03_shot01.mp4 --method M5 --model runs/detect/ball_ring_v1/weights/best.pt --execution realtime --async-detection --s2-hz 15 --history-frames 30 --max-replay-frames 15 --no-preview --output results/models/M5_async

# ライブ入力：カメラの実動作fpsも確認する

```

| 比較軸 | 指定と意味 |
| --- | --- |
| 球検出頻度 | `--s2-hz 10/15/20/30`を個別実行。`0`は毎処理フレーム |
| System 1間引き | `--s1-stride 2`は入力2枚に1枚。60fps入力なら要求30Hz |
| 選手候補 | `--players P0/P1/P2`：不使用／単一／近傍群。探索効果はG3と組み合わせる |
| Lost探索 | `--search G0/G1/G2/G3`：全画面／2×2タイル／外周優先／予測・選手ROI |
| ring-zone | `--ring-policy R0/R1/R2/R3/R4`：なし／観測優先／ROI優先／検出頻度増／R1+R2 |
| blob純粋版 | M1/M6に`--pure-blob`。fallbackありと区別する |

表のスラッシュは選択肢で、実行時には1つだけ指定する。全オプションは`--help`を参照。
詳細ルールの具体的な処理と限界は[実験仕様](EXPERIMENT_PROTOCOL.md)を確認する。
同じ要求Hzでも実検出回数・GPU負荷が同じとは限らない。ROI数や推論時間も併記する。
動画realtimeは処理が遅れたフレームを捨て、欠落率として残す。offlineの処理速度を
そのまま「カメラで60fps・P95<50msを達成」と解釈しない。

### 手順7：追跡・検出・得点を別々に評価する

```powershell
python evaluate_tracking_experiment.py --ground-truth datasets/annotations/day03_shot01.csv --predictions results/models/M2_15hz/tracking.csv results/models/M3_15hz/tracking.csv results/models/M4_15hz/tracking.csv results/models/M5_15hz/tracking.csv results/models/M6_15hz/tracking.csv results/models/M1/tracking.csv --iou-threshold 0.5 --epsilon 0.05 --lost-k 3 --recovery-m 3 --window 0.5 --output results/comparison_day03.json
```

TSR@IoU0.5、AUC、CLE/NCLEの平均・中央値・P95、リング相対誤差、出力／有効Coverage、

得点判定は固定したLSTM・同じ前処理で全構成を比較する。
`ring_x,ring_y`、missing mask、`source`、`observation_age_s`を保存してあり、
選手の推定位置や未来フレームによる補間を真の球観測に置き換えない。
LSTM自体は今回未実装。判定結果ができたら[シュート結果の形式例](experiment_examples/score_predictions.csv)に
`shot_id,actual,predicted`を記録し、追跡失敗でも行を消さず`predicted=unknown`とする。


モデル・閾値の選択はvalで完了してからtestへ進む。資料の60fps・P95<50ms・Score F1≥0.90は
目標値であり、このコードを追加した時点での実測結果ではない。

### 4. YOLOによる追跡

YOLOがボールを検出するため、手動ROI選択は不要。標準モデル `yolo26n.pt` は
`sports ball` を対象とし、リングの検出や得点判定は行わない。
モデルが手元にない場合、初回実行時にダウンロードされることがある。

#### ByteTrackで追跡結果をまとめて保存

```powershell
# カメラ映像を追跡
python yolo_bytetrack_live.py --camera-index 1

# 撮影済み動画を追跡
python yolo_bytetrack_video.py --video "results/recordings/experiment01.mp4"

# 画面を表示せず、先頭100フレームを処理
python yolo_bytetrack_video.py --video "results/recordings/experiment01.mp4" --no-display --max-frames 100
```

実行ごとに `results/yolo/live_日時/` または `results/yolo/video_日時/` を作成する。

| ファイル | 内容 |
| :--- | :--- |
| `tracking.csv` | フレーム番号、検出成否、ID、信頼度、中心・矩形座標、処理時間、入力時刻 |
| `tracked.mp4` | 矩形・ID・軌跡を描画した動画 |
| `raw.mp4` | 描画前の取得映像をMP4に再圧縮したもの（カメラ版のみ） |
| `snapshots/` | `S` キーで保存したJPG画像 |

カメラ版は `--video` を使用できず、動画版は `--video` が必須。
両方ともByteTrack専用。動画は先頭から順に処理し、末尾で終了する。
表示中は `S` で画像保存、`Q` またはEscで終了する。**YOLO版に `P` による録画停止機能はない。**

#### BoT-SORTや個別の保存先を使う

```powershell

# 独自学習モデルを使用。class-idはモデル内のボールのIDに合わせる

```

#### YOLO版でよく使う設定

以下はByteTrack専用版と汎用版で共通。全オプションは各プログラムの `--help` を参照。

| オプション | 既定値 | 用途 |
| :--- | :--- | :--- |
| `--model` | `yolo26n.pt` | 検出モデルを変更 |
| `--class-id` | ボール系クラス名から検索 | 独自モデルの対象クラスを指定 |
| `--confidence` | `0.10` | 検出信頼度の閾値 |
| `--iou` | `0.5` | NMSのIoU閾値 |
| `--image-size` | `960` | 入力画像サイズ。大きくすると処理負荷も増える |
| `--device` | `auto` | CUDAが使えればGPU 0。`cpu`、`0`等も指定可能 |

詳しいCSVの意味と実験上の注意は [YOLO＋ByteTrackの使い方](YOLO_ByteTrack_使い方.md)を参照。

### 5. 適応的追跡と評価

固定カメラ・単一ボールの動画を対象に、YOLO・KCF・等速カルマンフィルタを切り替える。
不確実性や遮蔽の疑いで再検出し、リング付近では観測を優先する。
実映像での精度改善や先行研究に対する新規性は未検証で、得点判定は含まない。

#### 追跡を実行

```powershell
# ringの数値は例。元動画上のリング矩形に置き換える
python adaptive_basketball_tracker.py --video "sample.mp4" --ring 820 180 90 25 --mode adaptive --output results/adaptive/run01 --record
```

`--video` と `--ring X Y W H` は必須。リングは元動画の左上を原点とする
ピクセル座標で、左上のx・y、幅・高さを指定する。自動検出や選択画面はない。
`--output` は**未作成のディレクトリ**を指定し、省略時は `results/adaptive/` 以下に自動作成する。

| 設定 | 内容 |
| :--- | :--- |
| `--mode adaptive` | すべての適応的切り替えを使う（既定） |
| `--mode yolo` | 毎フレームYOLOで検出 |
| `--mode fixed` | 固定間隔でYOLO、間をKCF＋カルマンで追跡 |
| `--mode no-ring` | リング付近の特別処理を除いて比較 |
| `--mode no-uncertainty` | 不確実性スコアによる再検出を除いて比較 |
| `--detect-interval 6` | 通常時の検出間隔（既定6フレーム） |
| `--max-prediction 12` | 観測できないときの予測期限（既定12フレーム） |
| `--confidence 0.15` | 検出閾値（YOLO＋ByteTrack版とは既定値が異なる） |
| `--record` | 結果動画を保存するフラグ。パスは付けない |
| `--no-preview` | 表示なしで処理 |
| `--fps <数値>` | 入力動画FPSを上書き。FPS情報がない場合にも指定 |

出力は `tracking.csv`、`config.json`、`--record` 指定時の `tracking.mp4`。
CSVには切り替え理由、観測／予測／欠測の区別、中心座標、リング相対座標などを記録する。
表示中は `Q` またはEscで終了する。

#### 正解座標で評価

元動画に対する正解CSVを用意して実行する。フレーム番号は0始まり。
以下の座標は形式説明用であり、そのまま評価には使わない。

```csv
frame_index,center_x,center_y,visible,occluded,near_ring
0,100,200,1,0,0
1,,,0,1,0
2,130,180,1,0,1
```

```powershell
python evaluate_adaptive_tracking.py --ground-truth annotations.csv --predictions results/adaptive/run01/tracking.csv --threshold-px 20 --output results/adaptive/evaluation01.json
```

`--predictions` には複数の追跡CSVを並べて指定できる。出力JSONは未作成の名前を使う。
完全遮蔽などで座標を判断できない場合は、正解座標を空欄にする。
成功率・中心誤差・遮蔽後の復帰時間・検出回数等を集計する。
既存のOpenCV／ByteTrackのCSVをそのまま評価する用途ではない。

比較条件、注釈方法、評価指標の定義は [適応的追跡の実験ガイド](ADAPTIVE_TRACKING.md)を参照。
切り替えロジックの単体テストは `python -m unittest discover -p test_adaptive_tracking.py -v` で実行できる。

### 6. OpenCVによる比較実験

最初のフレームで追跡対象をドラッグして囲む（ROI選択）。
YOLOによる自動検出を使わず、指定した対象を追跡する。

#### 手法を選んで追跡する

```powershell
# カメラをCSRTで追跡
```

#### 保存先と上書き

| 保存先 | 内容 |
| :--- | :--- |
| `captures/` | カメラ確認・OpenCV追跡・汎用YOLOの静止画 |
| `results/recordings/` | 実験用の録画動画 |
| `results/yolo/live_日時/`、`results/yolo/video_日時/` | ByteTrack専用版の実行結果 |
| `results/yolo/` | 汎用YOLOの既定CSV |
| `results/adaptive/` | 適応的追跡・評価の結果 |
| `results/<tracker>/` | OpenCV追跡の結果 |

個別に指定するCSV・MP4は、実験ごとに名前を変えて上書きを避ける。
適応的追跡の出力ディレクトリと評価JSONは、既存の保存先を指定するとエラーになる。
`captures/`、`results/`、`*.pt`、`編集済み元データ/` は `.gitignore` の対象なので、
これらの実験データはGitHubへのpushだけではバックアップされない。

#### 録画時間の扱い

| プログラム | 保存動画の時間基準 |
| :--- | :--- |
| カメラ録画・OpenCV汎用追跡・KCF専用追跡 | 同期ライターがフレームを複製・間引きし、カメラでは実時間、動画入力では元動画FPSに合わせる |
| YOLO＋ByteTrack／BoT-SORT（専用版を含む） | 取得・推論したフレームを固定FPSで保存。カメラ処理が遅いと、実時間より短く再生される場合がある |
| 適応的追跡 | 処理フレームを入力動画FPS（`--fps` 指定時はその値）で保存 |

YOLOカメラ版の実時間解析にはCSVの `source_seconds` を使う。
同一条件の方式比較には、別途録画した動画を入力する。

#### よくある問題

| 症状 | 確認すること |
| :--- | :--- |
| `ModuleNotFoundError` | `sys.executable` で実行環境を確認し、その環境の依存関係を確認する |
| `No Python at ...` | `.venv` 作成時のPythonがなくなっていないか確認する |
| カメラが映らない | カメラ番号、USB接続、他アプリによるカメラ使用を確認する |
| KCF等を生成できない | OpenCVのcontrib版と必要なトラッカーAPIを確認する |
| GPUが使われない | 共通準備のCUDA確認を実行。YOLOは `--device cpu` でも起動できる |
| 保存先が既に存在する | 適応的追跡では未作成の出力先を指定する |
| オプションが認識されない | YOLOは `--no-display`、録画・適応的追跡は `--no-preview`。`--record` も適応的追跡だけフラグ形式 |

購入予定金額のみを表示する場合は `python budget.py` を実行する。ファイル出力はない。
`adaptive_tracking.py`、`project_runtime.py`、`synchronized_video_writer.py` は他のプログラムから使う共通処理。
研究手順の補足は [追跡実験の準備](tracking_experiment_setup.md)と[追跡手法のまとめ](tracking_method_summary.md)を参照。
