# 体育館での撮影・リアルタイム追跡の準備（2026-11-26）

11/26に体育館で行う次の3つについて、今のプログラムで実施できるかを確認し、足りないものを作りました。当日の手順は [DAY_PROCEDURE.md](DAY_PROCEDURE.md) にまとめています。

1. リアルタイム追跡（ボールの追跡精度のみ）を2種類のモデルで行う
2. リアルタイム追跡にシュート判定（成功・失敗）をつける
3. 魚眼レンズで動画を撮影する

## 1. リアルタイム追跡：2種類のモデル

`scripts/realtime_tracking.py`（カメラ入力、3秒遅れで表示）は、これまで条件Gしか動かせませんでした。今回、実験用スクリプトと同じ選択肢を追加し、次の2種類をカメラ入力で起動できるようにしました。

| モデル | 中身 | 追加した引数 |
|---|---|---|
| A：条件G | 今までどおり。YOLOは1秒に最大15回、間はLK追跡 | なし |
| B：G＋ROI、上限30回/秒 | 追跡中はボール付近だけをYOLOにかけ、毎フレーム呼ぶ | `--roi-imgsz 320 --max-interval 1 --max-yolo-hz 30` |

ほかに、カメラ映像をそのまま保存する `--record-raw`（あとで正解を付けて精度を測るため）を追加しました。

experiment10での精度（AC電源、録画ファイルで測定。詳しくは [11/25のレポート7章](../2026-11-25-yolo-budget-alternatives/README.md)）：

| 入力サイズ | モデル | TSR@0.5（bridge後） | 実効fps |
|---|---|---:|---:|
| 960 | A：条件G | 82.5% | 55.1 |
| 960 | B：ROI＋30回/秒 | 90.0% | 44.5 |
| 704 | A：条件G | 81.7% | 72.7 |
| 704 | B：ROI（320）＋30回/秒 | 84.9% | 49.8 |
| 704 | B：ROI（256）＋30回/秒 | 85.9% | 52.5 |

入力704の3行は今回追加で測ったものです（[summary_704.json](summary_704.json)、各1回）。704でもモデルBはAより3〜4ポイント高くなりました。ただし704ではROI 1回の時間（12.5ms）と全画面1回の時間（18.2ms）の差が小さく、ROIで速くなる効果は960のときより小さくなります。

**注意：バッテリーだけで動かしたときの速度は、モデルBではまだ測っていません。** 11/16の測定では、バッテリー駆動だと入力960のYOLOが1回90〜135msかかり、30fpsに追いつきませんでした（暫定設定は入力704）。モデルBは毎フレームYOLOを呼ぶので、バッテリーでは処理が追いつかず、フレームの間引きが増える可能性があります。そのため当日の手順では、**試合の前に録画ファイルで1分間ずつ動かし、間引き率を見てから設定を決める**ようにしています（DAY_PROCEDURE.mdの手順3）。

## 2. シュート判定

### アルゴリズム（`src/shot.py`）

カメラは三脚で固定するので、最初に1回だけ、リングを囲む四角を画面上でドラッグして指定します（`--select-rim`）。四角の上下の真ん中を「リングの高さ」、左右の端を「リングの口」とみなします。あとは追跡したボールの中心の動きだけで判定します。

1. **シュートの始まり**：ボールがリングより上の「接近エリア」に入ったら、シュートの可能性ありとして見張り始めます。接近エリアは、横はリングの中心からリング半径の4倍まで、縦はリングの高さから160px上までです。
2. **リングの高さを上から下へ通過したとき**：通過した瞬間の横位置（前後のフレームから計算）がリングの口の中（少し余裕あり）なら「通過」とします。口の外なら「失敗」です。
3. **通過のあと**：
   - リングより25px以上下で、横位置がリングの口の中なら **成功**
   - そのままボールが見えなくなったら（ネットに隠れた）**成功**
   - リングより上に戻ったら（リングに弾かれた）**失敗**
   - リングより下でも、横位置が口の外なら（リングの横に落ちた）**失敗**
4. **通過しないまま接近エリアを出たとき**：リングに60px以内まで近づいていたら **失敗**（リングやボードに当たって外れた）。近づいていなければシュートではなかった（パスなど）とみなし、数えません。

判定は3秒遅れの補正済みの軌跡に対して行うので、表示と同時に「SHOT MADE／MISS」と累計（例：made 3 / 5）が画面に出ます。結果は `shots.jsonl` にも保存されます。

閾値はすべて、試しに決めた初期値です。3.の「横位置が口の外なら失敗」だけは、experiment12で成功と誤判定した1本を見て追加しました（下の表）。

### 限界

- 2D画像だけで判定しているので、ボールがリングの手前や奥を通った場合は区別できません。カメラはリングを横から（真横に近い角度で）見る位置に置くのが有利です。
- 確認に使った映像は3本・24本だけで、目視の判定は1人（Claude）が行いました。当日の映像で、本人が確認する必要があります。
- 追跡がリング付近でボールを見失うと（ネットの前、選手と重なる）、シュートを数え落とします。

## 3. 魚眼レンズでの撮影

撮影プログラムはすでにあります（リポジトリ直下）。

| プログラム | 用途 |
|---|---|
| `camera_video_recorder.py` | 1台を録画（Qで終了、Pで一時停止） |
| `dual_camera_recorder.py` | 2台を同じ時刻基準で録画（Mで同期マーカー） |
| `elp_camera_demo.py` | ライブ表示と静止画保存（Sで保存）。チェッカーボードの撮影に使う |
| `basketball_tracking_midterm/scripts/fisheye_calibrate.py` | チェッカーボード動画から魚眼レンズの補正値を計算 |

今回、**`camera_probe.py`** を追加しました。接続中のカメラを番号0〜4で探し、解像度とfpsの組み合わせごとに「実際に読めた画像の大きさ」と「実測fps」を表示します。OpenCVは、カメラが対応していない解像度を要求されてもエラーを出さずに別の解像度で動くことがあるので、当日は最初にこれで確認します。

確認したこと（カメラ未接続のため、魚眼カメラ本体では未確認）：
- このPCには内蔵カメラがあり、番号0で見つかりました（1920×1080・1280×720・640×480で約30fps）。**外付けの魚眼カメラは番号1以降になる可能性が高い**ので、`--camera-index` の指定を忘れないようにしてください。
- 録画プログラムは、要求と違う解像度・fpsで動いた場合も止まらず、実際の値を `session.json` に記録します。fpsは、カメラが申告した値が使えないときは要求した値で保存します（`synchronized_video_writer.py`）。
