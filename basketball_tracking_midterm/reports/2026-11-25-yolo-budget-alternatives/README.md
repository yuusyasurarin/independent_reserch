# YOLO呼び出し上限の集計と、2つの代替案（2026-11-25）

条件G（YOLOv5s・960・fプロファイル・bridge）が、YOLOの呼び出し上限（1秒あたり15回）にどのくらいぶつかっているかを集計しました。あわせて、上限にぶつかる原因への対策として2つの代替案を実装し、比較しました。

**重要：この環境には experiment10 の映像も追加学習済みの重みもありません（どちらもリポジトリ外のPCにだけあります）。** そのため、ここにある精度の数字はすべて**合成映像と疑似YOLO**によるものです。experiment10 での本当の精度は、6章のコマンドをPCで実行して測る必要があります。

## 1. 上限にどれくらいぶつかっているか（実データの記録から）

2026-10-27の条件Fの実行記録（`reports/2026-10-27-condition-f/evidence.json`）を使いました。条件Gも前段の処理は同じで、YOLO回数も同じ1,076回です。

| 項目 | s | m |
|---|---:|---:|
| YOLO回数（2,512フレーム） | 1,076（12.85回/秒、上限の86%） | 1,109 |
| 上限で止められたフレーム | 148（5.9%） | 211（8.4%） |
| 呼んだ理由：LK失敗（flow_unreliable） | 488（45%） | 587（53%） |
| 呼んだ理由：定期（3フレームごと） | 417（39%） | 434（39%） |
| 呼んだ理由：見失い探索（lost_search） | 157（15%） | 77（7%） |
| 呼んだ理由：急な動き（motion_change） | 14（1%） | 11（1%） |

「1秒の窓が上限で埋まっていたフレームの割合」は、フレームごとのログ（`online.jsonl`）が必要です。そのログはPCにしかないため、集計スクリプト `scripts/analyze_yolo_budget.py` を用意しました（6章）。

## 2. 代替案のアルゴリズム

### 代替案1：テンプレートマッチング追跡（`--frontend template`、`src/alternatives.py` の `TemplateBallPolicy`）

今のLKは、ボールの中の「角（コーナー）」を特徴点として最大30点取り、それが次のフレームでどこへ動いたかを追います。ところがボールは直径30px前後と小さく、模様も少ないので、角があまり取れません。速く動いてブレると、点が4点未満になって失敗します。

テンプレートマッチングでは、点を使わずに**ボールの見た目そのもの**を探します。

1. YOLOがボールを見つけたら、その枠を少し広げた範囲のカラー画像を「お手本（テンプレート）」として保存します。
2. 次のフレームでは、速度から予測した位置の周りに探索範囲を決めます（ボール直径の1.5倍、または移動量の3倍の余白）。
3. 探索範囲の中でお手本をずらしながら重ね合わせ、各位置の似ている度合い（正規化相互相関、−1〜1）を計算します。
4. 最も似ている位置の値が0.6以上ならそこをボールの位置とします。0.6未満（隠れた・大きくブレた）ならYOLOを呼びます。
5. お手本はYOLOで検出されるたびに作り直します。追跡結果からは作り直さないので、少しずつずれていく「ドリフト」が起きません。

YOLOを呼ぶタイミング・上限・候補の選び方・bridge補正は、条件Gとまったく同じです。

### 代替案2：予測位置の周りだけYOLO（ROI）（`--roi-imgsz 320`、`RoiScheduler`）

今は毎回、画面全体（1280×720）を960×960に縮めてYOLOに入れています。でもボールを追跡できている間は、ボールは予測位置の近くにしかいません。

1. 追跡できているときは、予測位置を中心に**427×427pxの正方形**を切り抜き、320×320に縮めてYOLOに入れます。縮小率は全体を960に縮めるときと同じ0.75なので、ボールは学習時と同じ大きさで写ります。
2. 見失っているとき（lost_search）は、画面全体でYOLOを使います。
3. 切り抜きの外で起きたことを見逃さないよう、**5回に1回は画面全体**で検出します。
4. 入力の画素数は320²/960²で約1/9になります。CPU実測では1回あたり116ms → 23ms（約1/5）でした。

1回が軽くなるので、**上限を30回/秒（毎フレーム）に上げても、計算量は今の条件Gと同じくらい**に収まります。上限にぶつかる問題そのものを、計算量を増やさずに解消できる可能性があります。

## 3. 合成映像での比較（疑似YOLO、5本×900フレーム）

`scripts/simulate_frontends.py` で比較しました。合成映像の内容は、1280×720のコート風の床、直径28pxのボール（陰影とモーションブラーつき）、ドリブル・パス・シュートの動き、横切る選手による隠れです。YOLOの代わりに「正解の枠に誤差を加え、10%は見逃し、5%は誤検出を出す」疑似検出器を使いました。結果は [synthetic_simulation.json](synthetic_simulation.json) にあります。

| 方式 | YOLO回数/秒 | 上限で止められたフレーム（/900） | TSR@0.5（補正前） | TSR@0.5（bridge後） | 計算量（全画面＝1） |
|---|---:|---:|---:|---:|---:|
| 条件G（LK） | 13.8 | 141 | 76.5% | 81.5% | 1.00 |
| 代替案1（テンプレート） | 13.3 | 60 | 79.9% | 80.0% | 1.00 |
| 条件G＋ROI | 13.8 | 140 | 76.0% | 81.1% | 0.38 |
| 代替案1＋ROI | 13.3 | 58 | 78.0% | 79.1% | 0.36 |
| 条件G＋ROI、上限30回/秒 | 30.0 | 0 | 95.3% | 96.7% | 0.37 |
| 代替案1＋ROI、上限30回/秒 | 30.0 | 0 | 92.8% | 95.3% | 0.36 |

呼んだ理由の内訳（合成）：LKは「LK失敗」が61%で、実データの45%と同じ傾向でした。テンプレートでは「LK失敗」にあたる理由が27%に減り、代わりに「急な動き」が28%に増えます。ドリブルの反転をテンプレートが正確に捉えるため、速度の急変として検出されるようになったためです。

**合成映像から言えること**
- テンプレート追跡では、System 1が失敗する回数と、上限で止められる回数が半分以下になりました。ただし、補正後の精度はほとんど変わりませんでした。
- ROIで呼び出しのスケジュールを変えないと、精度は同じまま計算量が約1/3になります。
- ROIで上限を30回/秒にすると、計算量は今と同じくらい（YOLO 1回分の全画面相当で、11回分/秒 対 13.8回分/秒）のまま、精度が大きく上がりました。

**言えないこと**
疑似YOLOは「呼べば正解近くを返す」ので、YOLOを呼ぶ回数が多いほど有利になります。本物のYOLOは見逃しや誤検出がもっと複雑ですし、ボールが選手と重なる場面も多くあります。ここでの差は「方向性」として見てください。experiment10での数字は、6章の実行で確かめる必要があります。

## 4. 速度（クラウドCPUで実測、GPUなし）

[cloud_cpu_roi_benchmark.json](cloud_cpu_roi_benchmark.json)（Xeon 2.3GHz 4コア、公式yolov5s.pt）

| 処理 | 1回あたり |
|---|---:|
| YOLO 全画面（960） | 115.7ms |
| YOLO ROI（320） | 23.0ms |
| System 1：LK | 0.7ms |
| System 1：テンプレート | 1.2ms |

GPU（RTX 3050 Ti、AC電源）での見積もりは次のとおりです（推定、未測定）。ROIの320入力は全画面の1/3程度（約9ms）と仮定しました。小さい画像はGPUの効率が下がるので、1/9にはならないと考えています。

| 方式 | 1秒あたりの負荷（見積もり） |
|---|---:|
| 現在の条件G：12.85×27ms＋30×8ms | 約590ms |
| ROI＋上限30回/秒：6×27ms（全画面）＋24×9ms（ROI）＋30×8ms | 約620ms |

どちらもリアルタイム（1000ms未満）に収まる見込みです。CPUだけの場合は、ROI＋30回/秒でも約1,360msになり、リアルタイムには届きません。

## 5. 現時点の判断

- 上限に近い状態で動いている主な原因は、LKの失敗の多さです。これは実データ・合成の両方で確認できました。
- **試す価値が大きいのは代替案2（ROI＋上限引き上げ）**です。計算量を増やさずにYOLOをほぼ毎フレーム呼べます。
- 代替案1（テンプレート）は、上限にぶつかる回数を減らす効果はあります。ただ、精度向上はまだ確認できていません。

## 6. PCで実際の精度を測る手順

`basketball_tracking_midterm` 直下で実行します。1本あたり数分かかります（GPU）。

```powershell
# 0) 既存Gの上限集計（10/27・11/16の結果フォルダに online.jsonl があれば）
.\.venv\Scripts\python.exe scripts/analyze_yolo_budget.py results/condition_g/fresh/s_G_f_bridge_960_cuda0_20261027T095044774094Z

# 1) 基準：今の条件G
.\.venv\Scripts\python.exe scripts/run_fixed_lag.py --condition G --output results/alt_20261125 --no-video
# 2) 代替案1：テンプレート
.\.venv\Scripts\python.exe scripts/run_fixed_lag.py --condition G --frontend template --output results/alt_20261125 --no-video
# 3) 代替案2：ROI（同じスケジュール）
.\.venv\Scripts\python.exe scripts/run_fixed_lag.py --condition G --roi-imgsz 320 --output results/alt_20261125 --no-video
# 4) 代替案2：ROI＋上限30回/秒（毎フレーム）
.\.venv\Scripts\python.exe scripts/run_fixed_lag.py --condition G --roi-imgsz 320 --max-interval 1 --max-yolo-hz 30 --output results/alt_20261125 --no-video
# 5) 代替案1＋2
.\.venv\Scripts\python.exe scripts/run_fixed_lag.py --condition G --frontend template --roi-imgsz 320 --max-interval 1 --max-yolo-hz 30 --output results/alt_20261125 --no-video

# 各runの上限集計
.\.venv\Scripts\python.exe scripts/analyze_yolo_budget.py (Get-ChildItem results/alt_20261125 -Directory).FullName --json results/alt_20261125/budget.json
```

各runの `metrics.json` を見て比べます。見る項目は、`tracking.tsr_iou_05`（精度）、`performance.processing_fps`（速度）、`performance.relative_inference_pixels`（計算量）、`performance.roi_calls`（全画面とROIの回数）です。

注意点：
- ROIの320入力は、valで選んだ設定（960）とは違います。そのため、結果は「experiment10での開発実験」という扱いになります。
- テンプレートの閾値0.6・余白・5回に1回の全画面は工学的な初期値で、調整はしていません。
