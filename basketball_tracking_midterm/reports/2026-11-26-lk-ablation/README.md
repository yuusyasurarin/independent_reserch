# LKは本当に必要か：LKを抜いた比較（2026-11-26）

bridge補正では、前後0.4秒以内にYOLOの検出があるとLKの位置を使わずに直線で結びます。そこで「LKは要らないのではないか」を確かめるため、LKを抜いた版を作ってexperiment10で比べました。

## LKなし版（`--frontend nolk`、`src/alternatives.py` の `NoLKBallPolicy`）

- LKの追跡をしません。YOLOを呼ばないフレームでは、直近のYOLOの位置から求めた速度で、等速に進めた位置を使います。
- YOLOは `--max-interval` フレームごとに定期的に呼びます。LKが失敗したときや急な動きのときに早めに呼ぶ、という判断はなくなります。見失ったときの探索（3フレームに1回、全画面）は同じです。
- 候補の選び方、2回連続での乗り換え、0.3秒での失効、上限（1秒15回）、bridge補正、ROIの使い方は、今のモデルとまったく同じです。

## 結果（experiment10、AC電源、録画ファイルを全速で処理、各1回）

速度の比較は、同じ時間帯に測った値どうしで行っています。今回の測定は前夜より全体に遅く、モデル1が前夜の72.7fpsに対して今回は30.1fpsでした（充電中で、GPUの状態が違った可能性があります。原因は未確認）。そのため、fpsは表の中だけで比べてください。

## わかったこと

1. **YOLOの回数を減らしたままLKを抜くと、精度が大きく落ちます。** 3フレームごと（10回/秒）では、モデル1の81.7%が75.3%に、モデル2の84.6%が79.8%に下がりました。LKは、YOLOを呼ばない間に「ボールがどこにいるか」と「次にいつYOLOを呼ぶか」を決めていて、その分だけYOLOの回数を節約できています。
2. **LKの代わりにYOLOを2フレームごと（15回/秒）に増やすと、精度は同じか少し上になります。** 入力704では83.3%（モデル1より＋1.6ポイント）、ROIでは84.4%（モデル2とほぼ同じ）でした。処理fpsもほぼ同じでした（28.8 対 30.1、37.3 対 38.5）。LK自体の計算は1フレーム1ms程度と軽いので、速度の差はほとんどYOLOの回数で決まります。
3. **補正前の位置では、LKありのほうが良いです**（モデル1：76.5% 対 73.3%、モデル2：80.2% 対 75.1%）。表示を遅らせずにその場の位置を使う場合（例えば将来、遅延なしでシュート判定をする場合）は、LKが役に立ちます。
4. **YOLOを毎フレーム呼べるなら、LKは要りません**（86.6%）。ただしAC電源でも処理が15fpsしか出ず、リアルタイムには間に合いません。

## まとめ：LKの役割

- bridge補正で消えるのは「YOLOとYOLOの間の位置」だけです。LKは「YOLOをいつ呼ぶか」と「候補を選ぶときの予測位置」に使われていて、YOLOが少ないときに効きます。
- 今回のexperiment10では、「LK＋YOLO約13回/秒」と「LKなし＋YOLO 15回/秒」がほぼ同じ速さ・同じ精度でした。どちらを選ぶかは、バッテリー駆動のときにYOLOを15回/秒呼べるかどうかで決まります。11/26 0時台の測定では、バッテリーではモデル1でも17〜24%のフレームを間引いていたので、YOLOを増やす「LKなし＋2フレームごと」は、もっと間引きが増える可能性があります。**まだバッテリーでは測っていません。**

## 限界

- experiment10の1本、各設定1回の測定です。同じ設定でも2.4ポイント程度ぶれることがあります。
- 速度は充電中のAC電源で、前夜の測定とは条件が違います。
